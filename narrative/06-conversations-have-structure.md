# Conversations Have Structure

## At a glance

- **Version:** 0.1 — draft
- **Date:** 2026-08-22

- **Requires:** nothing. No tooling, capture, or account.
- **Creates the question:** When multiple failure reports arrive with the identical symptom of “it won't connect,” how do session structures reveal the true root cause and owner?

---

By the end of my second month at Harrowmere Equipment Group, I had developed a healthy respect for the difference between a user's experience and a technical fact.

When users opened trouble tickets, they described the physical reality in front of them: a spinning progress icon, a dialog box that popped up instantly with an error code, or a screen that simply froze until the operating system gave up. But because they lacked visibility into the underlying protocols, they summarized every variation into the exact same sentence:

*“The network is down. It won't connect.”*

On Thursday morning, that single sentence triggered an escalating dispute across three different engineering pods.

The finance department had rolled out an updated client build that communicated with four backend services across our datacenter:
- A user account directory at `198.51.100.30`
- A transaction processing gateway at `198.51.100.20`
- A financial data export API at `198.51.100.50`
- A quarterly reporting repository at `198.51.100.40`

Within twenty minutes of the morning login rush, four tickets arrived in our queue from four different department leads. 
One complained that clicking the directory service resulted in an instant connection failure. 
Another reported that the transaction gateway hung indefinitely before displaying a timeout. 
A third claimed the export API was intolerably slow. 
A fourth stated that quarterly reporting generated half of a report and then abruptly crashed.

Owen Kline from Network Engineering was already standing in the aisle near our desks, his arms crossed over a company fleece, defending his infrastructure against an impatient application admin.

“The core switches are clean,” Owen said firmly. “BGP routing tables are converged, interface error counters are zero across the trunk links, and latency to the datacenter is under three hundred microseconds. This isn’t a network problem. It’s an application bug.”

Leah Moreno stepped out from her office, holding a laptop showing a stack trace.

“Our application code hasn’t changed since Friday,” Leah countered. “Our services are running in healthy containers. But when users initiate requests from the floor, they get transport connection errors. If our services are listening and the user gets a socket error, the network is dropping packets.”

I sat at my terminal, caught between the two senior engineers. To me, all four tickets sounded like facets of the same overarching incident. The users couldn’t reach the backend; therefore, something in the communication path was broken.

Dana Shah walked over from the manager’s station and stopped beside my chair. She tapped the edge of my desk with a notebook.

“Ethan,” Dana said quietly. “Don’t participate in a shouting match between network and application silos. Open the packet capture from the client workstation and check the conversation records in [[zeek_conn_log|Zeek conn.log]].”

I opened the capture file—`06-failures.pcap`—and queried the six connection records generated by the client host during its morning attempt:

```
source.port  destination.ip   destination.port  event.duration  connection.state  connection.history
41001        198.51.100.30    80                0.000011        REJ               Sr
41000        198.51.100.20    80                4.092267        S0                S
41003        198.51.100.50    80                4.000853        SF                ShADadfF
41002        198.51.100.40    80                0.000471        RSTR              ShADadr
```

Dana leaned over my shoulder. “Look at the `connection.state` column. What does it tell you?”

“It shows four different states,” I said. “`REJ`, `S0`, `SF`, and `RSTR`.”

“And what did the tickets say?”

“Every ticket said the application failed to connect.”

“Right,” Dana said. “The user sees a broken button. But the network conversation records the physical structure of how that conversation began, lived, or died. Show Owen and Leah the difference between the first two targets.”

I looked at the first target: `198.51.100.30`. 
The Zeek log listed `connection.state: REJ` with a duration of eleven microseconds, and the history field showed `Sr`.

I pulled up the exact packets in Wireshark:
- Frame 1: Client sends `[SYN]` on port 41001.
- Frame 2: Exactly 11 microseconds later, the server returns a [[tcp_rst_ack|`[RST, ACK]` packet]].

Owen leaned over the monitor, pointing at Frame 2.

“There,” Owen said. “Look at the delta timestamp. Eleven microseconds. That SYN traversed the local switch, reached the server, and the remote operating system immediately replied with a reset. For a machine to send a RST-ACK, its TCP stack has to be alive, the physical link has to be intact, and the routing path has to work in both directions.”

“Then why did it reject the connection?” I asked.

“Because nothing was listening on port 80,” Owen said. “Or the host firewall explicitly rejected the socket. That is a systems administration issue on that server. It is not a routing failure.”

“Now show them the second target,” Dana directed.

I brought up `198.51.100.20`. 
In Zeek, the state was [[conn_state_s0|`S0`]], with a duration of four seconds and a history of simply `S`.

I examined Frames 21 through 28 in Wireshark. The client sent an initial `[SYN]` packet. One second later, having received nothing back, it retransmitted. Two seconds later, it retransmitted again. Then three seconds, then four seconds. Across eleven seconds of total capture time, the client sent eight successive SYN packets with `[[exponential_backoff|exponential backoff]]`.

Not a single byte returned from the destination.

“Now compare that to the first target,” Dana said to me. “What is the difference between `REJ` and `S0`?”

The contrast was striking. 

“In `[[conn_state_rej|REJ]]`,” I explained, “the remote machine answered. The path worked, but the server actively refused the connection. In `S0`, nobody answered. The SYN packets went into a black hole. Either the routing path failed, or an inline firewall dropped the packets silently without sending an ICMP unreachable or a reset.”

Owen looked at Leah. “`198.51.100.20` is sitting behind the secondary perimeter firewall. Someone updated an access control rule last night.”

“And `198.51.100.30` was supposed to have its web service started after the reboot,” Leah admitted, typing a quick message into her team’s chat channel. “The system service failed to start on boot.”

With two queries, two completely separate teams had been assigned their respective issues without a minute of wasted debate.

“What about the other two?” I asked, looking back at the logs. “Target `198.51.100.50` says `SF`. That’s a normal, successful connection. Why did the user complain that the export was slow?”

I inspected the Wireshark stream for `198.51.100.50`.
- Frame 11: Client sends `[SYN]`.
- Frame 12: Server returns `[SYN, ACK]` in 0.0000 seconds.
- Frame 13: Client sends `[ACK]`.
- Frame 14: Client sends `GET /api/v2/export?page=1` (95 bytes).
- Frame 15: Server immediately returns a transport `[ACK]`, confirming receipt of the request.
- Frame 16: Exactly 4.0004 seconds later, the server sends `HTTP/1.1 200 OK` (132 bytes).
- Frame 18: Clean `[FIN, ACK]` teardown.

I looked at the four-second gap between Frame 15 and Frame 16.

“Between Frame 15 and Frame 16, there are no retransmissions,” I observed. “There are no dropped packets. The network delivered the request in two hundred microseconds, and the server’s network card acknowledged it instantly. Then the server spent four whole seconds generating the response before sending the HTTP payload.”

Leah winced slightly. “That’s our backend database export query. It runs an unindexed join on legacy tables before returning the JSON payload. The user waited four seconds because the database took four seconds to calculate the answer, not because the network was congested.”

“`[[frame_15_proof|Frame 15 is your proof]]`,” Dana noted. “The server acknowledged receipt of the HTTP GET immediately. That single ACK proves the network completed its job. Everything that happened after that was application latency.”

“And the fourth target?” Owen asked, pointing to `198.51.100.40`.

In Zeek, the connection was marked `[[conn_state_rstr|RSTR]]`—established, responder aborted.

In Wireshark, the client requested a quarterly report. The server responded with `HTTP/1.1 200 OK` and a response header stating `Content-Length: 5000`. But immediately after transmitting only 400 bytes of body data, the server abruptly sent a `[RST, ACK]` and severed the connection.

“The server promised five thousand bytes,” I said, reading the header. “And it only delivered four hundred before throwing a reset.”

“An unhandled application crash,” Leah diagnosed immediately. “The reporting daemon hit a buffer allocation error mid-stream and crashed, causing the operating system to reset the open socket.”

In ten minutes, four seemingly identical user reports had resolved into four distinct technical realities:
1. `REJ`: A stopped local service on the host.
2. `S0`: A silent firewall drop on the network path.
3. `SF` (4-second duration): A slow database query in the application.
4. `RSTR`: A backend crash midway through data transmission.

“None of those four was a mystery,” Dana said. “Each left a signature shaped exactly like the fault that caused it. An analyst who groups them all under ‘connectivity failure’ destroys the very information needed to fix them.”

She pulled up a second capture on my screen: `06-fragmentation.pcap`.

“Now,” Dana said, “look at a failure where the evidence doesn't leave a convenient error code.”

I examined the two packets in the capture. Both were UDP fragments carrying IP identification `0x5876`.
- Frame 1: Length 1396 bytes, `More Fragments` flag set to 1, Fragment Offset 0. Destination port: blank.
- Frame 2: Length 1100 bytes, `More Fragments` flag set to 0, Fragment Offset 172 (1,376 bytes). Destination port: 53 (DNS).

“A large DNS response was fragmented because the packet exceeded the [[path_mtu|Path MTU]] of 1,400 bytes,” I observed.

“Notice where the UDP destination port is displayed,” Dana instructed. “In Frame 1, Wireshark shows no port. In Frame 2, it shows port 53.”

“Why is port 53 only on the second frame?” I asked. “Isn't the UDP header at the beginning of the packet?”

“The UDP header is physically inside Frame 1,” Dana explained. “Wireshark only dissects the transport layer after reassembly is complete, which happens when the final fragment arrives. But look at what happens on the wire: a [[non_initial_fragment|non-initial fragment]] carries no UDP header at all. It has an IP header, and then raw payload bytes.”

She pointed at our firewall configuration guidelines on the shelf.

“Many firewalls and security appliances are configured to silently drop non-initial fragments because they cannot inspect port numbers inside them. If a network path drops that second fragment, what does the client experience?”

I thought about how IP reassembly works. If the second fragment never arrives, the operating system cannot reconstruct the datagram. It waits until its reassembly timer expires, and then silently discards the partial packet.

“The client experiences a timeout,” I said.

“And what appears in the Zeek log?” Dana asked.

I paused. “Nothing. If the datagram is never reassembled, the transport transaction never existed. There is no `REJ`. There is no `RSTR`. There is only silence.”

Dana closed the laptop lid and stood up.

“When systems fail, the conversations they leave behind have structure. They refuse, they drop, they stall, or they abort. Learn to read that structure before you assign an owner. Because if you cannot distinguish between an active refusal and a silent drop, you will spend your life fighting other people’s battles.”

Owen gave a nod of approval and walked back toward network engineering. Leah headed back to her developers to restart the directory daemon and optimize the database query.

I looked down at the four rows in my notebook. One user complaint, four different root causes, four different owners. 

I picked up my pen and began drafting the incident ticket update. For the first time, every sentence had an owner, a frame number, and an unambiguous reason why.

### Vocabulary & Concepts

| Term | Desk Translation |
|---|---|
| [`[RST, ACK]` Packet](#term-tcp_rst_ack) | An immediate transport-layer refusal sent by an operating system indicating that a packet reached the destination host, but no active application was listening on that port or a local policy actively rejected it. |
| [connection.state: S0](#term-conn_state_s0) | A Zeek connection state indicating that an opening SYN was observed from the client, but absolutely no response or acknowledgment was ever returned by the server or path. |
| [Path MTU](#term-path_mtu) | The maximum transmission unit (packet size in bytes) that can traverse an entire end-to-end network path without requiring IP fragmentation. |
| [Non-Initial Fragment](#term-non_initial_fragment) | Subsequent fragmented IP packets (with fragment offset > 0) that carry only payload bytes and lack the Layer 4 transport header (such as TCP or UDP ports), making them invisible to port-based firewall inspection rules. |
| [connection.state: REJ](#term-conn_state_rej) | Active transport refusal (`Sr`); server OS responded immediately with a reset packet in microseconds. |
| [connection.state: RSTR](#term-conn_state_rstr) | Established session aborted by responder (`ShADadr`); server returned partial data then sent reset. |
| [Immediate TCP ACK (Frame 15)](#term-frame_15_proof) | Immediate TCP ACK confirming instant network delivery before a 4-second application think time began. |
| [Exponential Backoff](#term-exponential_backoff) | Client TCP stack doubling retransmission delays across silence (1s, 2s, 4s) when packets are dropped. |
